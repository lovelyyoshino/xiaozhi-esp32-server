# CPU 服务器 + 云语音 API 调优记录

适用链路：设备 Opus → 本地 Silero VAD → 豆包/百炼流式 ASR → 云 LLM → 云 TTS。
本次只修改仓库代码；没有访问华为云生产实例，也没有调用付费语音 API。

## 已修改与收益

| 环节 | 修改 | 收益与边界 |
|---|---|---|
| VAD | 每连接独立 decoder、流式状态；共享模型加锁 | 防止不同设备污染识别状态；共享模型的推理仍串行执行 |
| VAD | PyTorch 默认 1 线程、启动预热、最多 4 个待处理推理 | 避免小模型争用计算线程，首次请求不再承担全部模型预热；不是 4 倍算力 |
| 音频接收 | 每连接有序异步消费者，队列最多 16 包 | 移除每连接一个常驻 ASR 消费线程；60 ms/包时队列最多存约 960 ms 音频，满载时通过 TCP 背压保留完整语音 |
| 音频背压 | 常态直接入队；满时等待消费，断连先取消等待入队任务再清空队列 | 不主动丢首音节；关闭后不再写回队列，避免 `queue.join()` 永久等待；持续过载仍会增加延迟 |
| 唤醒确认 | `short` 使用 180 ms 本地 WAV，编码帧缓存；音频准备完成后才发送 TTS start | 替换原 1.56 秒默认问候，音频长度少 1.38 秒；实际恢复收音还包括网络、设备与服务端缓冲，不能视为 180 ms 端到端响应 |
| 唤醒恢复 | 去掉唤醒后固定 2 秒屏蔽；异常或取消保证清除保护，必要时补 TTS stop | 避免确认结束后继续吞掉首句；播放保护期间仍可能忽略回采，不能恢复设备停录期间未采集的语音 |
| 后台任务 | 所有连接共享 16 个 worker，运行与排队总预算 16 | 原先 N 个连接各最多 5 个后台线程，改成此类线程进程内最多 16 个；仍有 TTS 和其他线程 |
| 拥塞/断连 | 任务拒绝时补 TTS stop；断连取消本连接排队任务 | 防止设备只收到 start 而一直等待；运行中的同步 API 请求仍需自然结束 |
| 上报 | 全进程 32 个名额，最多 1 份历史音频转换；异步复用管理端客户端 | 慢管理端不再无限积压历史记录；预算满时舍弃该次上报 |
| 豆包 ASR | gzip 等级 9 → 1，关闭 WebSocket 二次压缩 | 本机压缩耗时约降 33%，包体约增 1.6%；只针对该样本的压缩环节 |
| TTS 本地编码 | 新增 `server.tts_opus_complexity`，配置示例从 10 调至 5 | 本机 PCM → Opus 编码耗时约降 46%；保留帧格式与采样率，音质需听测；旧配置不填时保留 10 |
| 流式 ASR | ready 超时、预录顺序发送、停止幂等、短指令回归 | 避免丢首音节、重复发送和短指令被长度门槛过滤；上游网络故障仍可能失败 |
| 天气/地点 | 独立 4 线程、8 个任务预算；HTTPS、请求超时、固定城市开关 | 慢同步查询不阻塞事件循环；固定场所不必依赖 IP 定位 |
| 智控台配置 | 保留本地 server 资源预算 | 本地设置不再因使用智控台而静默丢失 |

## 本机测量与估算

在 `main/xiaozhi-server` 下运行：

```bash
python -m pytest tests -q
python performance_tester/benchmark_cpu_audio.py --iterations 1000 --with-opus
```

2026-10-22 的微基准环境：x86_64，12 个逻辑 CPU，Python 3.10.12，PyTorch 2.4.1+cpu，opuslib_next 1.1.5。
本地缺少 Opus Python 依赖，验证时只安装到 `/tmp/xiaozhi-audio-check-deps`，以 `PYTHONPATH` 加载；未修改系统包。
项目固定的 PyTorch 版本为 2.2.2；上述本机运行环境与生产依赖版本的差异也需要在云端复测。

| 项目 | 结果 | 口径 |
|---|---:|---|
| Silero 32 ms 静音帧 | 平均 0.2243 ms，P95 0.2941 ms | 单线程 JIT 模型本身，1000 帧；不含解码、状态切换、线程调度和网络 |
| gzip 等级 9 | 0.0855 ms/包，1367.3 字节/包 | 16 kHz 单声道 WAV 切成 60 ms 包，5 轮中位耗时 |
| gzip 等级 1 | 0.0567 ms/包，1389.7 字节/包 | 与等级 9 使用相同样本；包体是平均值 |
| Opus 复杂度 10 | 0.8575 ms/包，154.7 字节/包 | 24 kHz 单声道、60 ms、24 kbps，含真实缓冲和编码，5 轮中位耗时 |
| Opus 复杂度 5 | 0.4637 ms/包，152.4 字节/包 | 相同样本与码率；不含重采样、网络、线程调度和播放；未评估主观音质 |

由此估算，单路持续音频的纯模型计算约为 `0.2243 / 32 = 0.70%` 个 CPU 核。
N 路约为 `0.0070 × N` 核的纯模型工作量；实际还有 Opus 解码、状态复制、锁、调度、TLS 和 TTS 编码。
共享模型锁还限制单进程的吞吐，不能将这个结果直接乘服务器核数作为设备容量。
100 个连接原先后台池的理论线程上限为 500；现在这部分上限为 16，下降 96.8%。
ThreadPoolExecutor 按需创建线程，此比例不等于实际内存或 CPU 降幅。

TTS 编码复杂度降低的收益只属于编码环节。按本机进程 CPU 时间估算，16 路持续播放
的纯编码工作量约从 0.229 核降至 0.124 核；不能声称整台 4 核服务器 CPU 降低 46%。
网络 TTS 仍可能需要本地解压/重采样/编码，而且原有 TTS 每连接的播报线程仍在，16 worker 并非全进程线程总量。

当前验证：80 项回归测试通过，覆盖真实 Silero 模型的跨连接状态隔离、音频消费顺序、
ASR 握手与短指令、预算归还、断连取消、插件调度、固定城市配置及真实 Opus 分块音频解码。
30 个修改或新增 Python 文件通过语法及 Pyflakes 检查，两份 YAML 通过解析与资源预算断言。
还覆盖短确认音与旧问候模式、动态文件丢失回退、发送异常与取消恢复、确认后的首包、真实音频发送状态顺序、
短突发任务恢复以及满队列时的保序与断连取消；180 ms 确认音可编码并解码为 3 个 60 ms Opus 包。
新增音频缓存模块此前通过局部 mypy 检查；未执行全项目类型检查。
云 API 通过替身验证协议流程，没有验证真实供应商响应、生产配置或端到端延迟。

## 华为云 4 vCPU / 8 GB 起始配置

用户确认 ECS 为 4 vCPU、8 GB；实例型号、地域、后台服务占用和供应商并发配额尚不明确。
先用一个 Python 服务进程和上述 16 worker / 16 总任务预算，VAD 保持单线程。
16 个 worker 主要等待云 API，不代表同时运行 16 份本地模型，也不代表只能连接 16 台设备。
先验证单进程负载，再考虑两个进程分担独立模型锁；多进程会额外占用模型内存、连接和 API 配额。

| 负载 | 起始验收档位 | 判定依据 |
|---|---|---|
| 仅连接、无持续音频 | 50 → 100 → 200 连接 | 看 RSS、线程数、心跳和连接初始化拥塞；这些是测试档位，不是已验证容量 |
| 持续发送音频 | 10 → 20 → 40 → 60 路 | 看 CPU、音频队列、VAD 调度延迟；长连设备即使没人说话也可能持续发送静音 |
| 同时发起云回复 | 4 → 8 → 12 → 16 个任务 | 看首音频 P95、预算拒绝率、上游 429 和完整回复耗时 |

假设每个后台任务平均占用 worker 为 2–4 秒，16 worker 的理论满负载吞吐约为 4–8 个任务/秒。
为减少等待，按 60% 占用率估算，初始请求负载约为 2.4–4.8 个任务/秒；这是计算示例，
不是实测容量，任务占用时间要包含完整 LLM 流、工具等待等，不能用首包延迟代替。
并发、ASR/TTS 配额、CPU 和网络任意一项先到上限，都会缩小可用容量。
正式运行前宜保留约 30% CPU 余量；如果同机还跑智控台、Java、数据库，需要一并统计资源占用。

## 部署配置

将这些键合并到已有 `data/.config.yaml` 的对应位置，保留已有密钥与地址；不要替换整份文件。
没有智控台时，VAD 配置也可以使用下列片段覆盖默认值。

```yaml
server:
  audio_queue_maxsize: 16
  wakeup_response_mode: short
  connection_worker_max: 16
  connection_max_pending: 16
  reply_admission_wait_ms: 200
  reply_busy_audio: config/assets/tts_notify.mp3
  reply_busy_text: "现在请求较多，请稍后再试。"
  report_max_pending: 32
  websocket_compression: null
  tts_opus_complexity: 5
VAD:
  SileroVAD:
    num_threads: 1
    max_pending_inferences: 4
```

使用智控台时，上述 `server` 键从本地透传；VAD、ASR、LLM、TTS 和插件配置在智控台对应位置修改。
本次工作区没有 `data/.config.yaml`，示例默认 ASR 仍是 FunASR，因此不能据此认定线上正在使用哪家 API。

| 目标 | 起始建议 | 取舍 |
|---|---|---|
| 减少回复排队（默认） | `connection_max_pending` 与 `connection_worker_max` 都设为 16 | 更早拒绝拥塞请求；可用并发仍受云端配额约束 |
| 吸收短突发（可选） | 将总任务预算提高到 32，保持 16 worker | 最多约一个批次等待，等待时间取决于前面的请求耗时 |
| VAD 稳定 | 1 个计算线程，4 个推理准入名额 | 不因连接数扩大 PyTorch 内部线程；加名额不等于加吞吐 |
| TTS 编码 CPU | `tts_opus_complexity: 5`；质量优先可恢复 10 | 只影响本地 PCM → Opus；保持 24 kbps 和原采样率/帧长，需比较人声音质 |
| 低延迟断句 | 百炼 `max_sentence_silence` 与本地静音阈值先试 200–350 ms | 嘈杂/混响需录音验证，过短可能切断自然停顿 |
| ASR 选择 | 豆包流式与百炼流式分别测量后选主服务 | 不对每句同时调用两家；跨云地域和 API 配额会影响结果 |
| LLM/TTS | 流式 LLM + 流式 TTS；普通请求使用 function_call 路径 | 避免再串行一次 intent_llm；TTS 要确认实际适配器支持流式，网络 API 不等于流式 API |

当前任务预算包含初始化、LLM 与直接播报。初始化遇到满额时关闭连接，由设备按正常重连策略重试。
运行中同步 HTTP 请求不能靠 Future.cancel 中止；其超时及厂商限流仍影响 worker 占用。

`wakeup_response_mode: short` 仅替换唤醒后的确认音，不调整唤醒词检测模型或 VAD 灵敏度。
该路径沿用现有开关：需要 `enable_greeting: true` 与 `enable_wakeup_words_response_cache: true`；智控台模式也需检查对应远端配置。
`cached` 保留动态问候，动态文件读取失败时回退到静态短音；短模式不会后台调用云 TTS 刷新问候。
新音频为 `main/xiaozhi-server/config/assets/wakeup_confirm.wav`：16 kHz、单声道、16 位 PCM、180 ms、带淡入淡出。
它是提示音而非语音，不向对话历史写入没有说出的问候。旧模式没有指定时仍使用 cached；默认配置和智控台本地模板显式选择 short。
如开启 `enable_stop_tts_notify`，播报结束还会叠加其提示音；当前默认关闭，应避免两段提示叠加后延长停录。

繁忙反馈默认只有提示音和文字状态，尚无预录的“请稍后”人声；无屏幕设备需配置合适的本地繁忙语音，才能用听觉区分繁忙和已唤醒。

## 延迟预算与线上验收

目标按“用户说完 → 设备首段可播放音频”定义，区别于 ASR 首字或 LLM 首 token。

| 阶段 | 初始预算（估算，非实测） |
|---|---:|
| 静音与断句 | 200–350 ms |
| ASR 最终结果及上行网络 | 100–250 ms |
| LLM 可供合成的首段文本 | 150–350 ms |
| 流式 TTS 首包 | 150–300 ms |
| 下行与设备缓冲 | 50–100 ms |
| 合计 | 650–1350 ms，另加排队及网络波动 |

0.8–1.5 秒是短指令、无工具外部查询、无拥塞时的优化目标。天气、地点等额外 API 查询不能套用该预算。
华为云上分开测试“连接但不发音频”“持续发音频”“同时触发云 API”三类负载，
每类逐级增加设备数，记录 CPU、RSS、线程数、API 限流率、排队时间和首音频 P50/P95。
长期保持 CPU 余量；若音频队列经常达到上限，说明本地 VAD/网络事件循环已经落后，
先减少每进程活跃设备或增加进程分片，再讨论扩大任务队列。扩大队列只能增加延迟，不能提升识别能力。

## 地点与嘈杂环境

固定场所部署时，在天气插件配置 `use_ip_location: false` 和 `default_location`，
在地点插件配置 `use_ip_location: false` 和 `default_city`，两处填同一实际城市。
IP 只提供粗粒度地区，默认城市也只是城市级搜索；移动导盲的“我附近”仍需设备上送 GNSS/定位，当前补丁没有增加该协议。

VAD 判断有人说话，不负责分离目标人声。上述服务器改动解决并发卡顿和缓存边界，未实现波束形成、RNNoise 或 WPE。
优先在手柄端做近讲拾音/AEC、轻量降噪与按键短指令；阵列硬件确认后再试延迟求和与方向门控。
保留同一批真实大厅/食堂录音，用关键词召回、误触发和端到端延迟验证效果；波束形成收益取决于阵列几何和目标方向，不能用单麦数据推算。
危急“停下”宜有设备本地按键/本地控制通道，不应依赖云 API 往返。

## 以唤醒与对话体验约束性能优化

仓库客户端 `py_xiaozhi/src/application.py` 中，唤醒词在设备端检测；服务端 Silero VAD 用于判断语音起止，
不能提高尚未命中的端侧唤醒词召回。客户端收到 TTS start 会停止上行，因此服务器优化无法恢复这段时间内未上传的音频。
本次未修改客户端；取消固定屏蔽、缩短确认音只能减少服务端造成的等待，提示音期间连续说话仍需真机验证。

| 优先级 | 措施与状态 | 性能收益/估算 | 体验边界 |
|---|---|---|---|
| P0 已实现 | 本地 180 ms 确认音，动态问候可切回 | 相比默认 1.56 秒问候，音频时长约少 88%；不产生本轮云 TTS 请求 | 当前来自服务器，仍依赖网络和设备恢复监听；未测用户主观偏好 |
| P0 已实现 | VAD 状态隔离、单线程预热，音频有序消费 | 限制线程争用，常态入队不创建等待任务；整体 CPU 降幅需云端实测 | 不提高 VAD 阈值、不按负载抽掉用户音频 |
| P0 待设备端 | 唤醒命中立即本地确认，连接建立与录音并行，保存唤醒后 300–600 ms 预录 | 本地确认目标 100–300 ms；16 kHz 单声道 16 位 PCM 的 300–600 ms 缓存约 9.6–19.2 KB | 不能只在服务端缓存；需处理提示音回采、发送顺序和旧会话音频 |
| P0 待实测 | 常用地域的流式 ASR + 流式 LLM + 流式 TTS；ASR 主备按故障切换 | 短请求从说完到首音频目标 0.8–1.5 秒，排队与工具查询另计 | 不对每句话双发两家 ASR，避免翻倍调用；恢复时不重复执行工具 |
| P1 待联调 | 设备近讲拾音、AEC，再评估轻量降噪 | 设备处理后只上传单通道，云 CPU 不随阵列算法增加 | 降噪强度过高也会损伤辅音，唤醒词与 ASR 都须比较原始/增强录音 |
| P1 待录音评估 | 安静与嘈杂场景分别调断句，保留按键说话 | 短指令静音阈值先试 200–350 ms；停顿明显的用户可试 400–700 ms | 噪声底不等于目标人声；不能靠提高能量门槛节省 VAD 推理 |
| P1 待云端压测 | 负载上涨先暂停非必要音频上报，再扩容/分片 | 为实时 VAD 与网络留约 30% CPU 余量 | 不通过无限加队列伪装容量，不为每个在线设备预建付费 ASR 会话 |

上线验收使用同一批安静/大厅/食堂录音和真机用户，分别统计唤醒词召回、误唤醒、唤醒后第一句完整率、
断句截断率、繁忙反馈率与“说完到首音频”的 P50/P95。先以 10、20、40 路持续音频逐级验证，
以唤醒与首句指标相对原版本不退步作为约束；不能仅以平均 CPU 降低宣布优化成功。
4 vCPU 的初始保守负载可先测 10–20 路活跃音频、4–8 路同时回复，再向文中的档位递增；这些是测试档位，尚非承诺容量。
